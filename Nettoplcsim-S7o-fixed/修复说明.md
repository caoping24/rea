# NetToPLCsim S7o v1.2.5.0 — 屏保/关屏后 UI 卡死 修复说明

修复目标：**Windows 下长时间运行、或运行中触发屏幕保护程序 / 关闭显示器后，NetToPLCsim 页面按钮无响应、只能重启的问题。**

---

## 一、根因（已用源码 + 二进制逆向双重确认）

程序里存在一条**可无限期阻塞的跨线程链路**，一旦 S7ONLINE 驱动在空闲/关屏后不再回数据，就会把整个程序（含 UI）挂死。

1. **S7 消息泵线程**（`PlcS7onlineMsgPump`，一个在独立后台线程跑的隐藏 WinForms 消息循环）在收到驱动的 `WM_SINEC` 通知后，调用
   `SCP_receive(m_connectionHandle, 0, ...)` —— **超时参数 = 0**，即无限期等待。驱动在空闲/关屏后一旦停止投递数据，这个调用就**永远不返回**，消息泵线程被卡死，其窗口消息循环停止泵消息。
2. 所有对消息泵窗口的通讯都用**同步 `SendMessage`**（`IsoToS7online.cs` 里 `ExitPlcsimMessagePump` 发 `WM_M_EXIT`、`SendDataToPlcsim` 发 `WM_M_SENDDATA`、`InitPlcsim` 发 `WM_M_CONNECTPLCSIM`）。`SendMessage` 会一直等到目标窗口处理完消息才返回。
3. 于是：一旦消息泵线程卡死在 `SCP_receive` 里，**任何线程向它 `SendMessage` 都会永久阻塞**。尤其是**停止服务器 / 关闭程序时，UI 线程**会调 `stop()` → `ExitPlcsimMessagePump()` → `SendMessage(WM_M_EXIT)`，**UI 线程就此挂死**，页面按钮全无响应，只能强杀进程重启。
4. 叠加 `TcpServer.Stop()/DropConnection` 里的 `lock(this)`，即使不是 UI 线程先卡，一个被 `SendMessage` 卡住的线程持有锁，也会拖死 UI 线程的 Stop()。

> 一句话：**S7 泵线程可无限期阻塞 + 对外用同步 SendMessage，= 一旦驱动空闲挂住，全体陪葬。**

---

## 二、修改内容（7 处，仅托管层，不动协议/握手逻辑）

| 文件 | 改动 |
|---|---|
| `IsoToS7online.cs` | 新增 `user32.dll PostMessage` P/Invoke |
| `IsoToS7online.cs` | `ExitPlcsimMessagePump()`：发 `WM_M_EXIT` 由 `SendMessage` 改为 **`PostMessage`（异步，立即返回）** —— 停止/关闭永不因泵卡死而阻塞 UI |
| `IsoToS7online.cs` | `InitPlcsim()`：`m_autoEvent_MsgPumpThreadStart.WaitOne()` 改为 **`WaitOne(3000)`**，超时即失败 |
| `IsoToS7online.cs` | `InitPlcsim()`：`m_autoEvent_ConnectPlcsim.WaitOne()` 改为 **`WaitOne(3000)`**，超时即失败 |
| `PlcS7onlineMsgPump.cs` | `ReceiveFromPlcsimDirect()`：`SCP_receive(..., 0, ...)` 改为 **`SCP_receive(..., 5000, ...)`（5 秒有界超时）** |
| `PlcS7onlineMsgPumpS7.cs` | `ReceiveFromPlcsimAndSendBack()`：`SCP_receive(..., 0, ...)` 改为 **`5000`** |
| `PlcS7onlineMsgPumpTia.cs` | `ReceiveFromPlcsimAndSendBack()`：`SCP_receive(..., 0, ...)` 改为 **`5000`** |

**为什么这样改能解决卡死：**

- 泵线程的 `SCP_receive` 从"无限期阻塞"变为"最多等 5 秒"，驱动空闲挂住时它会超时返回，**消息泵不再永久卡死**，`WM_M_SENDDATA`/`WM_M_EXIT` 都能被处理。
- 即使极端情况下泵仍不响应，`WM_M_EXIT` 改为 `PostMessage` 后**停止/关闭不再阻塞 UI**，UI 永远不会因这条链路卡死。
- `InitPlcsim` 的两个等待加上 3 秒上限，连接握手也不会无限期占住 `TcpServer` 的锁。

正常工作时 S7ONLINE 用异步 `WM_SINEC` 通知、数据已就绪，`SCP_receive` 几乎立即返回，5 秒超时**不会误触发**，不影响正常通讯与握手。

## 五、注意事项 / 已知保留点

- **SCP_receive 超时单位**：`S7onlinx.dll` 为西门子专有接口，无公开文档。按业界通行语义，其第 2 个参数单位为毫秒，`0` 表示无限期等待，故取 `5000`（5 秒）。若实测发现单位不是毫秒，请反馈，我据实调整为合适值（此改动不影响 `PostMessage` 修复带来的"UI 不再卡死"保证）。
- 本修复为**最小、低风险补丁**：只改了等待与通讯方式，未改动任何 S7comm/S7commPlus 握手、TPKT/TPDU 解析、消息泵状态机逻辑。若你后续希望更深层加固（如泵线程加看门狗、数据路径也改异步并管理缓冲生命周期），可再继续。
